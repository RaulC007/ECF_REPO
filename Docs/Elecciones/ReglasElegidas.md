# Reglas Elegidas
## Ramas
El nombre de las ramas en las que se trabajara se especifica en las issues, para luego hacer PR con los cambios correspondientes a esa issue.

## Commits 
Los commits se nombraran como su misma rama en la que se trabaja con el númrero 1, si se hacen más de un commit se coloca el número siguiente y en caso de querer testear algo, se puede hacer un PR, para ver como se vera cierta funcion o informacion en GH, si no es la version final o no cumple con lo esperado se rechaza el PR y se siguen con los commits.

## PR´s
Para que un PR sea integrado es necesaria una revisión por un miembro del equipo distinto al que hace el PR, no es necesaria una descripción, eso se puede acordar por otros medios de comunicación.

## Integración
Para integrar los PR se hara uso de Merge Pull Requests, para añadir los cambios a main.

## Protección
La rama protegida será main, de tal forma que otro integrande tendra que validar el PR, para que se le pueda hacer merge a main.

## Robot
En caso de que se usara uno, lo más importante que tendria que verificar seria que no exista ningun conflicto entre las ramas, otra cosa que podria verificar es que la rama cumple con el nombre y formato establecido.

## Conflictos y Errores
Se asignara un issue especifico a los integrantes y se trabajara desde carpetas para que no haya conflicto entre ramas, y en caso de haber errores, se regresara el PR, para que se le hagan los cambios correspondientes.

# Reglas No Elegidas

- No es necesaria una proteccion tan robusta de las ramas, ya que el proyecto es muy simplre y corto y a su vez, somos muy pocas personas, por lo que es más facil controlar los PR de forma organizada.
- No habra muchas restricciones en los commits o ramas, los nombres y su proposito se especifican en los issues y en caso de errores, simplemente se comunica y se corrige.

# Cambios a Futuro
Estas reglas se estan tomando en cuenta para el estado actual del proyecto, tamaño del equipo, tiempo, recursos, etc. Pero en caso de que el proyecto avance y llegue a fases más avanzadas, es probable que será mejor añadir algunas otras que ahora se omiten; como una mejor protección de ramas, mejores especificaciones en los issues, PR´s y merges pull requests.
